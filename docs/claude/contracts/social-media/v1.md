# social-media adapter contract v1

This is the **normative** contract. Every adapter under `~/.bb-browser/sites/<site>/adapters/` for a social-media site MUST follow it. `tools/bb-eval` enforces it via the `SOC-*` check family. The narrative spec (the "why") lives at `docs/superpowers/specs/2026-06-18-social-media-design.md`.

## 1. Why this contract exists

`ecommerce` models transactions (buy things). `pharma-data` models record lookup. Neither captures the social-media use case: browse → read → engage → create. Forcing social-media into either loses half the signal (no cart/orders → ecommerce's P0 checks become N/A) or under-models the auth surface (no per-note tokens / captcha cooldowns in pharma-data's public/soft_vip/hard_wall tiers).

See `docs/claude/decisions/2026-06-18-why-social-media-contract.md` for the full rejection of the extend-existing-contracts option.

## 2. What counts as social-media

A site belongs to this domain if **all** are true:

- Primary content is **user-generated** (posts/notes/tweets/messages), not catalog items or database records.
- A **social graph** exists (users follow / friend / block other users).
- Engagement is **first-class** (like / favorite / comment / share / react).
- The agent's primary use case is **browse + read + engage + create**, not transact or look up structured data.

**In scope (2026-06-18):** Xiaohongshu (xiaohongshu.com / xhslink.com).
**Projected (per xiaohongshu-cli README):** twitter.com / x.com, bilibili.com, discord.com, telegram.org / t.me.

If a site mixes categories (e.g. a platform with both a shop and a social feed), pick the domain by the **user's primary use case** for the adapter being authored, not by the site overall.

## 3. Access tiers

Social-media authentication is 3-tier. Every adapter MUST declare its minimum tier in `@meta.accessTier` and return the tier actually in effect in `authStatus`.

| Tier | Meaning | Examples |
|---|---|---|
| `anonymous` | Works logged-out. Site serves content to unauthenticated clients. | XHS search (partial), twitter public profile reads |
| `auth_read` | Login required, but only to read. Cookie + maybe a request-scoped token. | XHS feed, most XHS endpoints |
| `auth_write` | Login required AND the account must be in good standing (not captcha-throttled, not rate-limited, signature current). | XHS like / comment / follow / post |

`authStatus` in the response reflects **the tier that was actually in effect for this call**, not the site's theoretical maximum. If a `like` call fails with `LOGIN_REQUIRED`, `authStatus` must be `anonymous` (the cookie was stale), not `auth_write`.

## 4. Canonical adapters

### P0 — the 13 canonical adapters

| Adapter | Intent | Read/Write | Required `accessTier` | Purpose |
|---|---|---|---|---|
| `auth` | manage | read | `anonymous` | Report current login state. No side effects. |
| `search` | discover | read | `auth_read`* | Keyword (+ optional topic/hashtag, sort, type, page) → `Note[]`. |
| `feed` | discover | read | `auth_read`* | Algorithmic / trending feed. `source` arg: `recommendation` \| `hot` \| `category` \| `following`. |
| `post-detail` | consume | read | `auth_read` | Single note/post by id. Resolves per-note access tokens (e.g. `xsecToken`) where applicable. |
| `comments` | consume | read | `auth_read` | Top-level comments on a post, paginated. `--all` auto-paginates into sub-comments. |
| `user` | consume | read | `auth_read` | User profile (nickname, redId, stats). |
| `user-notes` | consume | read | `auth_read` | A user's published / liked / favorited notes. Args: `whose` (me \| other), `which-list` (published \| liked \| favorited), `userId`. |
| `notifications` | consume | read | `auth_read` | Notification feed (mentions / likes / new followers). |
| `unread` | consume | read | `auth_read` | Unread counts across notification types. |
| `like` | engage | write | `auth_write` | Like (and `--undo` unlike) a post. |
| `favorite` | engage | write | `auth_write` | Bookmark (and undo) a post. |
| `comment-post` | engage | write | `auth_write` | Post a comment / reply on a post. |
| `follow` | engage | write | `auth_write` | Follow / unfollow a user. |
| `post-create` | create | write | `auth_write` | Publish a new post (image / video note). |

\* `search` / `feed` may partially work at `anonymous` on some sites. Declare `auth_read` as the tier needed for **full** results; the adapter returns `authStatus: anonymous` if the call succeeded logged-out.

### P1 — implement only when the site exposes them

| Adapter | Intent | When to implement |
|---|---|---|
| `post-delete` | manage | Site supports deleting own posts (XHS does). |
| `comment-delete` | manage | Site supports deleting own comments. |
| `dm-list` | consume | Site exposes direct messages (XHS web API doesn't; twitter does). |
| `dm-send` | engage | Site exposes DMs. |
| `follow-list` | consume | Site exposes who-a-user-follows. |
| `follower-list` | consume | Site exposes a-user's followers. |

### Forbidden adapter names (bb-eval SOC-6 FAILs)

| Name | Why forbidden | Correct approach |
|---|---|---|
| `feed-hot`, `feed-recommendation`, `feed-category`, `feed-following` | Filter-variant of `feed`. | `source` arg on `feed`. |
| `search-topic`, `search-hashtag`, `topics` | Topic is a keyword form. | `topic` / `hashtag` arg on `search`. |
| `user-posts`, `user-favorites`, `user-likes`, `favorites`, `likes` (as separate adapters) | Same intent ("list a user's notes"), different subset. | `which-list` arg on `user-notes`. |
| `feed-summary`, `note-summary` | The agent always wants full note objects. | Return full `Note` objects. |
| `hot-categories` | Dead-end enumeration adapter. | Document valid categories in adapter `description`. |
| `auto-login`, `login-flow` | AGENTS.md #5 — login is the human's job. | `auth` reports state only. |
| `*-debug`, `*-v2` | Dead-code variants. | Delete before merge. |

The rule behind this list: **one adapter per intent; fold filter-variants into args.** `feed-by-category` is forbidden (category is an arg); `search` vs `feed` vs `user-notes` are allowed (different intents).

## 5. Object model

All adapters return objects using these shapes. Field names are full-English camelCase. Every entity carries a `url`. Numeric stats are integers (agent-comparable); the raw site string is preserved in a parallel `*Label` field when the site formats it.

### `Note`

Returned by `search`, `feed`, `user-notes`, `notifications` (as array); returned in full by `post-detail`.

```jsonc
{
  "id": "noteId",                              // platform primary key
  "url": "https://www.xiaohongshu.com/explore/noteId?xsec_token=...",
  "type": "image" | "video",
  "title": "笔记标题",
  "desc": "正文",                              // full text only in post-detail; list adapters may return "" or truncated
  "author": { /* Author, see below */ },
  "tags": ["美食", "旅行"],                    // hashtag array
  "topics": [                                  // associated topics; post-detail only
    { "id": "topicId", "name": "旅行" }
  ],
  "stats": {
    "likes": 1234,                             // int, agent-comparable
    "likesLabel": "1234",                      // raw site string, preserved
    "collections": 56,
    "comments": 78,
    "shares": 9
  },
  "mediaCount": 9,                             // image count, or video duration seconds
  "publishedAt": "2026-06-10T08:30:00.000Z",   // ISO 8601 UTC; null if unknown
  "xsecToken": "...",                          // per-note access token; empty string on non-XHS sites
  "scrapedAt": "2026-06-18T10:00:00.000Z"
}
```

### `Author` (nested in `Note.author`)

The minimal form embedded in every Note.

```jsonc
{
  "id": "userId",
  "nickname": "昵称",
  "url": "https://www.xiaohongshu.com/user/profile/userId"
}
```

### `User` (returned by `user` adapter)

Full form. Shares field names with `Author` so the agent doesn't learn two schemas.

```jsonc
{
  "id": "userId",
  "nickname": "昵称",
  "redId": "小红书号",                        // platform public handle; empty on non-XHS sites
  "desc": "个人简介",
  "ipLocation": "IP 属地",
  "gender": "male" | "female" | "unknown",
  "url": "https://www.xiaohongshu.com/user/profile/userId",
  "stats": {
    "fans": 12000,                            // follower count
    "follows": 300,                           // following count
    "interaction": 45000                      // likes+collections composite (XHS metric)
  }
}
```

### `Comment`

Returned by `comments` and `comment-post` (as array / single).

```jsonc
{
  "id": "commentId",
  "noteId": "所属笔记 id",
  "author": { /* Author */ },
  "content": "评论正文",
  "stats": { "likes": 5, "subComments": 12 },
  "subComments": [ /* Comment[], recursive; comments adapter returns top-level only by default */ ],
  "createdAt": "2026-06-15T10:00:00.000Z",
  "url": "https://www.xiaohongshu.com/explore/noteId?comment=commentId"
}
```

### `WriteReceipt`

Returned by all write adapters (`like`, `favorite`, `comment-post`, `follow`, `post-create`, and P1 writes). Write adapters do NOT return the full Note/User — that's a read adapter's job. They return a lightweight receipt so the agent knows the action succeeded, whether it's undoable, and how to undo.

```jsonc
{
  "action": "like" | "unlike" | "favorite" | "unfavorite" | "comment" | "follow" | "unfollow" | "post",
  "targetId": "noteId | userId",               // the object acted upon
  "resultId": "commentId | newNoteId",         // only for comment / post-create
  "undoable": true,                            // whether the action can be reversed
  "undoAdapter": "like --undo",                // literal command string when undoable
  "undoHint": "Re-running `like` with --undo toggles the state back.",
  "url": "https://www.xiaohongshu.com/explore/newNoteId"
}
```

## 6. Response envelope

Every adapter — read or write, list or single — returns this envelope. `recommendedNextActions` lets the agent chain calls without learning each site's idiosyncrasies.

```jsonc
{
  "ok": true,                                  // false ⇒ error/hint/action MUST be set
  "data": <Note | Note[] | User | Comment[] | WriteReceipt | null>,
  "authStatus": "anonymous" | "auth_read" | "auth_write",
  "constraints": { /* list adapters only; see §6.2 */ },
  "pagination": { /* list adapters only; see §6.3 */ },
  "recommendedNextActions": [ /* always except `auth` */ ],
  "error": "LOGIN_REQUIRED",                   // present only when ok=false
  "hint": "Run `auth` adapter, then hand control to human for login.",
  "action": "stop_and_wait_for_human"
}
```

### 6.1 Error codes (fixed enum, each bound to one action)

The `error` field MUST be one of:

| `error` | When | `action` | What to do |
|---|---|---|---|
| `LOGIN_REQUIRED` | Site requires login to read. | `stop_and_wait_for_human` | Call `auth`; wait for human login. |
| `CAPTCHA_REQUIRED` | Site popped a captcha. | `stop_and_wait_for_human` | Human solves in-page, then retry. |
| `RATE_LIMITED` | Frequency cap hit (common on XHS writes). | `backoff_and_retry` | Wait 60–300s, then retry. Do NOT retry immediately. |
| `SIGNATURE_FAILED` | Request signature rejected (XHS `x-s`/`x-t` stale). | `refresh_and_retry` | Re-capture signature, re-issue. |
| `IP_BLOCKED` | IP banned / region-restricted. | `stop_and_wait_for_human` | Change proxy / environment; wait. |
| `NOT_FOUND` | noteId / userId doesn't exist or was deleted. | `abort` | Object unreachable; skip. |
| `PERMISSION_DENIED` | No access (private note / blocked). | `abort` | Skip. |
| `CONTENT_REJECTED` | Write content rejected (banned words, etc.). | `abort` | Revise content; retry. |
| `WRITE_FAILED` | Generic write failure. | `retry_or_abort` | One retry; abort if still failing. |
| `AUTH_EXPIRED` | Cookie / token expired. | `stop_and_wait_for_human` | Re-login. |

`action` is bound to the error — adapters MUST NOT invent new action values for these codes.

### 6.2 Constraints (list adapters)

List adapters (`search`, `feed`, `user-notes`, `comments`, `notifications`) MUST populate the constraint trio. Be honest: do not mark a constraint `executed` if you only acknowledged it.

```jsonc
"constraints": {
  "requestedConstraints": { "keyword": "咖啡", "sort": "latest", "type": "video" },
  "executedConstraints":   { "keyword": "咖啡", "sort": "latest" },
  "deferredConstraints":   { "type": "video" }   // not applied; tell the agent why in a hint
}
```

### 6.3 Pagination (list adapters)

Hybrid shape — surface both cursor and page so the agent picks the most robust path. `nextArgs` lets the agent copy-paste to the next call without understanding cursor semantics.

```jsonc
"pagination": {
  "page": 2,                                   // current page, 1-based
  "pageSize": 20,                              // count actually returned this page
  "hasMore": true,                             // raw site has_more flag
  "cursor": "next_cursor_string",              // cursor for cursor-based sites
  "nextArgs": { "cursor": "next_cursor_string" } // agent can pass this object directly as the next call's args
}
```

### 6.4 `recommendedNextActions`

Chains adapters. Example after `search`:

```jsonc
"recommendedNextActions": [
  { "adapter": "post-detail", "args": { "noteId": "abc", "xsecToken": "..." }, "why": "View full content of the top result." },
  { "adapter": "comments",    "args": { "noteId": "abc" },                       "why": "See engagement on the top result." }
]
```

After a write, point at undo or refresh:

```jsonc
"recommendedNextActions": [
  { "adapter": "like",        "args": { "noteId": "abc", "undo": true }, "why": "Undo this like if unintended." },
  { "adapter": "post-detail", "args": { "noteId": "abc" },                "why": "Re-read to confirm updated like count." }
]
```

## 7. `@meta` requirements

Every adapter's top-of-file `/* @meta { ... } */` block MUST include:

**Base fields (all domains):** `name`, `description`, `domain`, `args`, `capabilities`, `readOnly`, `example`.

**social-media-specific fields:**

| Field | Values | Purpose |
|---|---|---|
| `accessTier` | `anonymous` \| `auth_read` \| `auth_write` | Minimum tier this adapter needs. bb-eval SOC-2 enforces enum; SOC-5 cross-checks against `readOnly`. |
| `intent` | `discover` \| `consume` \| `engage` \| `create` \| `manage` | Which user-intent this adapter serves. bb-eval SOC-4 cross-checks against adapter name. |

Example `@meta` block:

```jsonc
/* @meta
{
  "name": "xiaohongshu/search",
  "description": "Search Xiaohongshu notes by keyword, topic, or hashtag. Supports sort (general/latest), type (image/video), pagination via cursor.",
  "domain": "social-media",
  "args": [
    { "name": "keyword", "type": "string", "required": true, "desc": "Search term, topic name, or #hashtag" },
    { "name": "sort", "type": "enum", "values": ["general", "latest"], "default": "general" },
    { "name": "type", "type": "enum", "values": ["image", "video"] },
    { "name": "cursor", "type": "string", "desc": "Pagination cursor from previous page's pagination.nextArgs" }
  ],
  "capabilities": ["read", "list"],
  "readOnly": true,
  "accessTier": "auth_read",
  "intent": "discover",
  "example": "bb-browser site xiaohongshu/search --keyword '咖啡推荐'"
}
*/
```

`@meta.name` MUST be `<site>/<adapter>` (e.g. `xiaohongshu/search`).

## 8. bb-eval SOC-* checks

`tools/bb-eval` enforces the following on every social-media adapter. Run before declaring done.

| ID | Check | Level |
|---|---|---|
| SOC-1 | `@meta.domain == 'social-media'` | FAIL |
| SOC-2 | `@meta.accessTier` is one of `anonymous` / `auth_read` / `auth_write` | FAIL |
| SOC-3 | `@meta.intent` is one of `discover` / `consume` / `engage` / `create` / `manage` | FAIL |
| SOC-4 | adapter-name ↔ intent consistency. (`feed` / `search` accept `discover` OR `consume`.) | FAIL |
| SOC-5 | write adapters (`like`, `favorite`, `comment-post`, `follow`, `post-create`, P1 writes) declare `readOnly: false`; read adapters declare `readOnly: true` | FAIL |
| SOC-6 | adapter local name is in the P0/P1 set; forbidden patterns fail | FAIL |
| SOC-7 | when source contains `error:`, it also contains `hint:` and `action:` | WARN |
| SOC-8 | `recommendedNextActions` present (except `auth`) | WARN |
| SOC-9 | list adapters (`search`, `feed`, `user-notes`, `comments`, `notifications`) contain `pagination` literal | WARN |
| SOC-10 | `authStatus` literal appears in source | FAIL |
| SOC-11 | first 50 lines declare `const HOME_URL = 'https://...'` | FAIL |
| SOC-12 | no hardcoded credentials (password/secret/Bearer) | FAIL |
| SOC-13 | token-cache logic evidence (`xsecToken` / `noteContext` / similar) | WARN |

**Static-checker caveats:** SOC-13 is WARN because grep can't verify runtime token propagation (same reasoning as PHR-6). SOC-7/8/9 are WARN because grep-based shape detection is coarse. All FAILs must be resolved before merge.

## 9. XHS-specific quirks (XHS-only; other sites skip this section)

These are XHS recon findings from `W:\tmp\xiaohongshu-cli`. They are documented here so XHS adapter authors don't re-derive them, but they are NOT generalized contract requirements.

### 9.1 `xsec_token` — per-note access token

Every Note returned from a listing (`search`, `feed`, `user-notes`) carries an `xsecToken` bound to its source (`pc_search` / `pc_feed` / `pc_explore`). Subsequent calls to `post-detail`, `comments`, `like`, etc. for that note MUST include this token or the request 403s.

Adapter responsibility:
- The Note object's `xsecToken` field surfaces it.
- Adapters MUST maintain an in-memory `noteId → xsecToken` cache populated by listing calls and consulted by detail/comment/like calls.
- bb-eval SOC-13 WARNs if the source shows no evidence of this cache (literal `xsecToken` / `noteContext`).

### 9.2 Request signing — `x-s` / `x-t` headers

XHS API requests require `x-s` (signature) and `x-t` (timestamp) headers computed per-request by a webpack-bundled JS module. This is tier-3. See the reverse-engineering playbook (`social-media-playbook.md`) for the signing-module injection pattern.

`SIGNATURE_FAILED` error + `refresh_and_retry` action is the recovery path.

### 9.3 Captcha cooldown

Aggressive write operations (rapid likes/follows) trigger captcha. The CLI observes a cooldown window. Adapter behavior:
- On `CAPTCHA_REQUIRED`, return the error and stop.
- Do NOT auto-retry within 60s.
- `RATE_LIMITED` recovery is `backoff_and_retry` with 60–300s delay.

### 9.4 SPA timing

XHS web is a Vue SPA. The three-phase wait strategy from `methodology/reverse-engineering/playbook.md` applies (wait old content gone → wait new content with expected child → wait count stable).
