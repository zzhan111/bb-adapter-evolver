# Ecommerce Adapter Contract v1

## Purpose

Defines the canonical adapter set for any ecommerce site, what each adapter must return, and what is **forbidden**. The contract exists because without it, adapters proliferate (see `~/.bb-browser/sites/ysbang/adapters/` — 38 files, most redundant).

**Primary consumer is an AI agent.** A human reading the JSON output is a secondary use case. Schema decisions favor the agent:
- Field names are full English words (`changePercent`, not `chgPct`)
- Values include units (`"¥123.45"`, not `123.45`)
- Every product carries a direct `url`
- Every failure includes `error` / `hint` / `action`
- Every successful response carries `recommendedNextActions` so an agent can chain calls

## The canonical adapter set

### P0 — required for any ecommerce site

These nine adapters cover every use case an agent or human needs. **Do not split these. Do not add filter-variants as separate adapters.**

| Adapter | Purpose | Read/Write |
|---|---|---|
| `auth` | Check login state. No side effects. | read |
| `search` | Keyword + structured filters → product list with pagination | read |
| `product` | Get product detail by id (sku-level if applicable) | read |
| `cart-list` | Current cart contents and totals | read |
| `cart-add` | Add a sku to cart (quantity, optional sku variant) | write |
| `cart-remove` | Remove or zero out a cart line | write |
| `checkout-preview` | Preview order: applied price, shipping, coupons. Does NOT submit. | read |
| `order-list` | Past orders with pagination and status filter | read |
| `order-detail` | Single order detail by id | read |

### P1 — only if the site has the concept

Implement only when the site genuinely supports it. Do not stub.

| Adapter | Implement when |
|---|---|
| `switch-store` | Site is multi-tenant (B2B pharmacy wholesale, marketplace seller console) |
| `coupon-list` / `coupon-claim` | Site has user-claimable coupons separate from auto-applied promotions |
| `address-list` | Site requires explicit address selection at checkout |
| `order-cancel` | Site supports user-initiated cancellation post-submit |
| `logistics` | Site exposes tracking distinct from `order-detail` |

### Forbidden

The following anti-patterns are **enforced rejection** by `bb-eval`:

| Pattern | Why forbidden | Correct approach |
|---|---|---|
| `search-by-<filter>` (price, factory, provider, expiration) | Multiplies surface area for no agent benefit | Pass filters as `search` arguments |
| `cart-summary` separate from `cart-list` | Agent always wants both; `cart-list` returns totals + items | One adapter, return both fields |
| `order-create` / `submit-order` | Side effects too large for agent autonomy without explicit human handoff | Use `checkout-preview`; require human to click submit in UI |
| `auto-purchase` / `regular-buy` workflow adapters | Orchestration belongs to recipes, not adapters | Compose P0 adapters in a recipe |
| `<adapter>-debug` variants left in production | Dead code | Delete before merge |

## Output schema (mandatory across all adapters)

Every adapter return value is an object with this top-level shape:

```jsonc
{
  "success": true | false,                    // required
  "error": "HTTP 401",                        // required if success=false
  "hint": "Need to log in to ysbang first",   // required if success=false; human-readable
  "action": "bb-browser open https://...",    // required if success=false; agent-executable; "" if no auto-fix
  "input": { /* echo of validated args */ },
  "url": "https://dian2.ysbang.cn/#/...",     // canonical entry url for this adapter
  "requestedConstraints": [...],              // see "Constraint tracking" below
  "executedConstraints": [...],
  "deferredConstraints": [...],
  "data": { /* adapter-specific payload */ }, // canonical envelope; specific shape per adapter
  "pagination": {                             // present when adapter returns a list
    "page": 1,
    "pageSize": 20,
    "totalItems": 137,
    "totalPages": 7,
    "hasMore": true,
    "nextCursor": "loadMoreKey-from-server"
  },
  "recommendedNextActions": [
    { "type": "filter" | "action" | "drill",
      "adapter": "cart-add",
      "args": { /* hint args */ },
      "reason": "you can add wholesaleId from results to cart" }
  ],
  "hints": ["short human-readable hints"]
}
```

### Constraint tracking (the one good thing from ysbang/search.js — keep)

Three lists let the agent know what was actually executed vs. what got dropped on the floor:

- **`requestedConstraints`** — every constraint the caller asked for, with source (`arg`, `keyword-parsed`, etc.)
- **`executedConstraints`** — what the adapter actually applied to the request or local filter
- **`deferredConstraints`** — what was acknowledged but not executed, with `recommendedAdapter` pointing to the next call

If `deferredConstraints` is non-empty, `recommendedNextActions` MUST contain a corresponding entry. `bb-eval` checks this.

### Product object (used by `search`, `product`, `cart-list`, `order-detail`)

```jsonc
{
  "id": "wholesaleId or skuId, whichever is the canonical handle",
  "skuId": "if site distinguishes spu/sku",
  "spuId": "if site distinguishes spu/sku",
  "name": "full product name as displayed",
  "brand": "extracted brand or empty",
  "spec": "100mg*48 grain",                   // packaging spec
  "manufacturer": "factory / vendor name",
  "providerName": "merchant for marketplaces, empty for first-party",
  "price": "¥123.45",                         // string with currency symbol
  "priceValue": 123.45,                       // numeric for comparisons
  "originalPrice": "¥150.00",                 // optional, before promotion
  "priceUnit": "盒",                          // optional
  "image": "https://cdn.example.com/...",     // direct CDN url
  "url": "https://www.example.com/p/123",     // direct product page
  "stockStatus": "available" | "out_of_stock" | "limited" | "preorder",
  "stockQuantity": 47,                        // optional
  "minOrderQuantity": 1
}
```


## URL declaration rule

Every adapter file must declare its destination URL constant in the **first 50 lines**, before any function logic. This is the single most-violated rule in past adapters and the reason we make it the top check.

```javascript
/* @meta
{
  "name": "ysbang/search",
  "domain": "dian2.ysbang.cn",
  ...
}
*/

async function(args) {
  const HOME_URL = 'https://dian2.ysbang.cn/#/home';
  const RESULT_URL = 'https://dian2.ysbang.cn/#/indexContent';
  // ... rest of adapter
}
```

`bb-eval` greps for a `const \w+_URL = '` (or `https://`) pattern in lines 1-50 and FAILs if missing.

## @meta block requirements

Every adapter must start with a `/* @meta { ... } */` block whose JSON contains:

- `name` — `<site>/<adapter>` (e.g. `"ysbang/search"`)
- `description` — one sentence in English describing the user/agent intent
- `domain` — primary host (e.g. `"dian2.ysbang.cn"`)
- `args` — object mapping arg-name to `{ required: bool, description: string }`
- `capabilities` — array, subset of `["dom", "network", "navigation", "writable"]`
- `readOnly` — boolean. Must be `false` if adapter mutates server state (cart-add, cart-remove)
- `example` — a runnable `bb-browser site ...` command (single line)

## Reverse-engineering tier expectations

Every ecommerce adapter except `auth` is expected to be **tier 2 or tier 3**:

| Tier | Auth | Effort | Examples |
|---|---|---|---|
| 1 | Cookie only, naive `fetch` | ~1 min | Public product pages without personalization |
| 2 | Bearer + CSRF / signed body | ~3 min | jd cart, pdd order list, ysbang most APIs |
| 3 | Webpack module injection / Pinia store / page-bound runtime | ~10-30 min | Pinned tokens, signed payloads only built inside the SPA |

If your `search` adapter is tier 1 on a logged-in B2C site, you are almost certainly wrong. Re-check by capturing network with `bb-browser network --with-body` while logged in.

## Versioning

This is `v1`. Future versions land at `docs/claude/contracts/ecommerce/v2.md` with a migration note pointing back. v1 stays frozen so existing adapters keep their evaluation reproducible.

## Open questions for v2

- Do we need a `category` adapter (browse by category tree)? Currently considered out-of-scope; agents should use `search` with a category filter argument.
- Should `checkout-preview` accept an explicit `couponIds[]` argument, or always return all applicable coupons and let the caller filter? Leaning toward the former.
- For multi-store B2B, should `search` be implicitly scoped to current store, or take a `storeId` arg? Current call: implicit, with `executedConstraints` declaring the active store.
