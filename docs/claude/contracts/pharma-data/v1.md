# Pharma-Data Adapter Contract v1

## Purpose

Defines the canonical adapter set for any **structured pharmaceutical / regulatory
/ market data station** — sites where the agent's primary intent is to look up
records (regulations, prices, quality notices, market data) about drugs,
companies, or policies. These sites have **no cart, no checkout, no orders**.

This contract is intentionally narrow. The existing
[`ecommerce`](../ecommerce/v1.md) contract is the correct home for B2C/B2B
commerce; do not use this contract for transactions.

**Primary consumer is an AI agent.** Schema decisions favor the agent, mirroring
ecommerce v1 conventions:
- Field names are full English words.
- Values include units where the site provides them.
- Every record carries a direct `url`.
- Every failure includes `error` / `hint` / `action`.
- Every successful response carries `recommendedNextActions`.

## The canonical adapter set

### P0 — required for every pharma-data database

| Adapter | Purpose | Read/Write |
|---|---|---|
| `auth` | Check login state. **Optional** — most public databases work without. No side effects. | read |
| `list` | Database-key + filters → page of records. Returns the canonical `Record` shape. | read |
| `item` | Detail by ID. Auto-detects numeric vs base64 ID. | read |

### P1 — implement only when the database has the concept

| Adapter | Implement when |
|---|---|
| `search` | The site exposes a keyword-search box distinct from `list` filters. Most sites do not need this — `list(keyword=...)` usually suffices. |
| `export` | The database has a CSV/Excel export button. Typically VIP-gated. |
| `related` | The database exposes "related records" links (e.g. policy → covered drug). |

### Helper (cross-cutting, NOT per-database)

| Helper | Purpose |
|---|---|
| `yaozh-auth` (or generic `<site>-auth`) | Cookie-injector. Reads a session cookie from input, attaches it to every subsequent request. **Does not perform login itself.** |

### Forbidden (enforced by `bb-eval` PHR checks)

| Pattern | Why forbidden | Correct approach |
|---|---|---|
| `<dbKey>-list` and `<dbKey>-detail` as separate adapter files | One adapter, two methods | Single adapter exporting `list` and `item` |
| `<filter>-list`, `<filter>-detail` | Multiplies surface area for no agent benefit | Pass filter as `list` argument |
| `<dbKey>-debug`, `<dbKey>-v2` | Dead code | Delete before merge |
| Auto-login workflow in any adapter | AGENTS.md #5 — login is the human's job | `auth` adapter reports state only; login happens in browser by human |
| Hardcoded credentials / API keys / `Bearer ` literals | Security; rotates frequently | Read from env / input at runtime |
| Adapter name not in the canonical set (`auth`, `list`, `item`, `search`, `export`, `related`) | Sprawl | Use a canonical name; if it doesn't fit, the contract is wrong, not the name |

## URL declaration rule

Every adapter file must declare its destination URL constant in the **first 50
lines**, before any function logic. For pharma-data, the URL must contain the
`dbKey` (e.g. `/yaopinjiage`).

```javascript
/* @meta
{
  "name": "yaozh/yaopinjiage",
  "domain": "pharma-data",
  "dbKey": "yaopinjiage",
  ...
}
*/

const HOME_URL = 'https://db.yaozh.com/yaopinjiage';
const DETAIL_URL = 'https://db.yaozh.com/yaopinjiage/<id>.html';
```

`bb-eval` greps for `const <DBKEY>_URL` or `HOME_URL` in lines 1-50 and
verifies the URL contains the `dbKey` slug.

## @meta block requirements

Every pharma-data adapter must start with a `/* @meta { ... } */` block whose
JSON contains:

| Field | Type | Notes |
|---|---|---|
| `name` | string | `<site>/<adapter>` (e.g. `"yaozh/yaopinjiage"`) |
| `description` | string | One sentence in English describing the user/agent intent |
| `domain` | string | **Must be `"pharma-data"`** — PHR-1 check |
| `dbKey` | string | The database slug, e.g. `"yaopinjiage"` — PHR-2 check |
| `authStatus` | string enum | One of `"public"`, `"soft_vip"`, `"hard_wall"` — describes this database's tier |
| `args` | object | arg-name → `{ required: bool, description: string }` |
| `capabilities` | array | subset of `["dom", "network", "navigation"]`. **No `"writable"`** — pharma-data is read-only. |
| `readOnly` | bool | **Must be `true`.** Pharma-data v1 has no write operations. |
| `example` | string | a runnable `bb-browser site ...` command (single line) |
| `kind` | string enum | Optional. Set to `"helper"` for cross-cutting adapters like `yaozh-auth`. PHR-9 check. |

## Output schema (mandatory across all pharma-data adapters)

The top-level envelope is the same as ecommerce v1:

```jsonc
{
  "success": true | false,                    // required
  "error": "HARD_LOGIN_WALL",                  // required if success=false; use a standard code
  "hint": "The /yaopinzhongbiao page requires a logged-in VIP session.",  // human-readable
  "action": "yaozh-auth",                      // agent-executable; "" if no auto-fix
  "input": { /* echo of validated args */ },
  "url": "https://db.yaozh.com/yaopinjiage",   // canonical entry url for this adapter
  "requestedConstraints": [...],              // see ecommerce contract for shape
  "executedConstraints": [...],
  "deferredConstraints": [...],
  "data": { /* adapter-specific payload */ },
  "pagination": {                             // present when adapter returns a list
    "page": 1,
    "pageSize": 20,
    "totalItems": 7370,
    "totalPages": 369,
    "hasMore": true,
    "nextCursor": null
  },
  "recommendedNextActions": [
    { "type": "drill",
      "adapter": "item",
      "args": { "id": "667063" },
      "reason": "this record has more fields on the detail page" }
  ],
  "hints": ["short human-readable hints"]
}
```

### `Record` object (used by `list`, returned in `data.records[]`)

```jsonc
{
  "dbKey": "yaopinjiage",
  "id": "667063",
  "title": "依替米星注射液 2ml:100mg",
  "url": "https://db.yaozh.com/yaopinjiage/667063.html",
  "fields": {
    "通用名": "依替米星",
    "剂型": "注射液",
    "规格": "2ml:100mg",
    "最高零售价": "21.30元",
    "执行日期": "2010-04-15"
  },
  "authStatus": "public",
  "vipGatedFields": [],
  "scrapedAt": "2026-06-16T10:30:00.000Z"
}
```

### `Detail` object (used by `item`, returned in `data`)

```jsonc
{
  "dbKey": "yaopinjiage",
  "id": "667063",
  "url": "https://db.yaozh.com/yaopinjiage/667063.html",
  "title": "依替米星注射液 2ml:100mg",
  "fields": { /* same key-value shape as Record.fields, plus any detail-only columns */ },
  "body": "free-text body of the detail page, trimmed",
  "attachments": [
    { "label": "原文PDF", "url": "https://..." }
  ],
  "authStatus": "public",
  "vipGatedFields": [],
  "scrapedAt": "2026-06-16T10:30:00.000Z"
}
```

### Authorization tiers (canonical)

| `authStatus` | Meaning | Adapter behavior |
|---|---|---|
| `public` | No auth required | Return all fields |
| `soft_vip` | Some cells redacted to "查看" placeholder | Return the record; list the redacted field names in `vipGatedFields`; do NOT fabricate values |
| `hard_wall` | The page never renders; server returns an interstitial / login redirect | Return `success: false` with `error: "HARD_LOGIN_WALL"`, `hint: <human-readable>`, `action: "yaozh-auth"` |

## Error model (standard codes)

The following error codes are **standardized** for this contract. `bb-eval`
will verify the string literal appears in the source. Free-form error strings
are allowed but get a WARN.

| Code | When | `action` shape |
|---|---|---|
| `LOGIN_REQUIRED` | A record / cell requires auth we don't have | `"yaozh-auth"` (the helper adapter name) |
| `HARD_LOGIN_WALL` | The page itself never renders for anonymous users | `"yaozh-auth"` |
| `ENCRYPTED_ID_DECODE_FAILED` | A base64 ID could not be decoded to a numeric ID | `""` — agent must re-list |
| `RATE_LIMITED` | The server returned a rate-limit / captcha page | `"wait <seconds>"` |
| `SCHEMA_DRIFT` | The page rendered but the table no longer has the expected columns | `""` — needs human investigation |
| `DBKEY_UNKNOWN` | Caller asked for a dbKey this adapter doesn't know | `""` — fix the call |

## ID type discrimination

Detail-page IDs come in two forms on db.yaozh.com:

| Form | Pattern | Example | Example URL |
|---|---|---|---|
| Numeric | `/^\d+$/` | `667063` | `/yaopinjiage/667063.html` |
| Base64-encoded | `/^[A-Za-z0-9_-]{10,}$/` | `aZSSb2NmbmdlnmxqnZeZmQ` | `/ypzl/aZSSb2NmbmdlnmxqnZeZmQ.html` |

The `item` adapter must:

1. Detect the ID form with a regex test.
2. For numeric IDs, build `<DETAIL_URL>/<id>.html` directly.
3. For base64 IDs, build `<DETAIL_URL>/<id>.html` directly **without** trying
   to decode the base64 (the server expects the encoded form, not the numeric
   one — this was verified on 2026-06-16 against `/ypzl`).
4. On any URL-construction failure, return `ENCRYPTED_ID_DECODE_FAILED`.

`bb-eval` PHR-6 (WARN) verifies a regex discriminator is present in the `item`
function source.

## Reverse-engineering tier expectations

| Database | Auth tier | Discovery effort | Notes |
|---|---|---|---|
| `policies`, `yaopinjiage`, `dijia` | public | Tier 1–2 — naive fetch + HTML parse | All public, no token |
| `ypzl`, `customs`, `ypxs` | public / soft_vip | Tier 2 — HTML parse + base64 ID handling | Cell redaction is site-side, not adapter-side |
| `yaopinzhongbiao` | hard_wall | Tier 3 — needs login + likely XHR endpoint discovery | Adapter cannot function without user-provided session |

## Versioning

This is `v1`. Future versions land at `docs/claude/contracts/pharma-data/v2.md`
with a migration note pointing back. v1 stays frozen so existing adapters keep
their evaluation reproducible.

## Open questions for v2

- **Cross-database joins** (e.g. find all policies mentioning a drug). Not
  adapter work; needs a query layer above. Deferred.
- **English version** at `data.yaozh.com`. Same backend, different skin. Worth
  supporting in v2.
- **`drugad` database**: `查看` links are `#` placeholders. Don't yet know if
  this is a click-handler, a soft-VIP gate, or a dead link. Deferred.
- **Pagination strategy**: `?page=N` works for <10k rows. For larger databases,
  an internal XHR endpoint would be better; discover opportunistically.
